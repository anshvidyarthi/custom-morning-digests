## Worth a deeper look

**MCP transitions to stateless architecture in July specification**

The May 21 release candidate locking for the Model Context Protocol specification represents the most significant architectural change since the protocol's November 2024 launch. The shift to stateless operation at the protocol layer addresses the primary scaling bottleneck that teams encountered when moving MCP servers from local development to production deployments.

The core challenge was session state. The original MCP specification included a protocol-level session identifier (Mcp-Session-Id) that required sticky routing—meaning once a client connected to a specific server instance, all subsequent requests from that client had to land on the same instance. For a single-server deployment, this is trivial. For a horizontally scaled service behind a load balancer, it requires either session-affinity configuration in the gateway or a shared session store (Redis, DynamoDB) accessible to all instances. Both patterns add operational complexity and create failure modes.

The July 28 specification removes session state from the protocol layer entirely. Under SEP-2567 and related proposals, any MCP request can now land on any server instance. The mechanism that makes this work is explicit state threading: servers that need to carry context across calls mint an explicit handle (basket_id, workflow_token) from a tool invocation and have the model pass it back as an ordinary argument on subsequent calls. The second major change is caching semantics. List and resource read results now carry ttlMs and cacheScope headers, modeled on HTTP Cache-Control. This means a client can cache tools/list responses for exactly as long as the server permits.

The operational implication is that MCP servers can now run behind commodity HTTP infrastructure—plain round-robin load balancers, standard reverse proxies, CDN edges—without special session handling. That lowers the barrier to deploying MCP servers as managed services and makes the protocol viable for use cases where stateful transport was a non-starter.

[Model Context Protocol Blog](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/)
